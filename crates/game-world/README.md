# game-world

`game-world` provides a generic host over one shared component store. `GenericHost<State, Event, Storage>` owns logical time, checked identity and event counters, typed records, and snapshots. Composition supplies the schema, typed state and events, contextual validation, and systems. An application storage wrapper implements the two-method `StorageAccess` interface; it retains the same single Store.

State and storage are separate fields for disjoint borrowing. `parts_mut()` also lends the existing event records without cloning them. `append_many` advances event sequence only; `bump_revision` publishes a caller revision, while `publish_many` advances both. Callers preflight the complete transaction budget before owner writes.

`ReadSet` records selected present or absent typed rows, entity presence, and scoped membership. Binding it to a batch admits an owner-bound `ReadGuard` over those opening facts, the admitted typed projections, and the exact writes; unrelated component edits do not invalidate a projection. `Transaction` combines one `Batch`, owner-bound `ReadGuard`s, allocation count, typed events, final logical time, and an explicit revision budget. Capture `transaction_opening()` before preparation; its opaque lineage prevents reuse across separate hosts, clones, or restores. `commit_transaction` rejects changed opening cursors or backwards time, preflights identity, event, and revision arithmetic, validates all guards, and checks identity reservations before applying the schema-validated batch. It then advances time and counters and publishes records as one admitted transaction. New entities must lie in the reserved ID interval. Rejected admission preserves component rows, counters, events, revisions, and runtime state. Owners validate their private metadata before host admission and finalize precomputed metadata infallibly after success.

`preview` and `preview_with_tail` build transient hosts from caller-selected storage and state at an existing logical opening. Each has independent affinity; the latter copies only the supplied pending event suffix. `events_since(cursor)` borrows records whose sequence exceeds the consumed cursor, including in a retained suffix. Previews produce candidate effects for source-side admission; complete saves come from the canonical host.

The playable `game-assembly` uses this host for live storage and generic counters. The host depends only on core types, the private ECS adapter, and the simulation engine. AssemblyState retains feature runtime metadata and application coordination; canonical per-entity rows live in the shared Store.

`OwnerSystem<Event>` runs feature workflows against `OwnerTxn`, which hides the application's state type. A `Registry<State, Event>` registers owner instances, pure `RuntimeSlot` field lenses, component write ownership, and typed `Request` receivers. Each runtime remains in its existing canonical state field and save format. Registry instances contain immutable execution configuration, not a second copy of live runtime state. Each field lens must read and write the same canonical field, perform only ordinary field access and assignment, and never panic. Slots must be disjoint: an owner's runtime cannot contain a due queue that is also registered separately, because installing the runtime would overwrite the queue's independently prepared changes. The composition supplies this trusted structural wiring; feature logic and fallible metadata changes belong in the journal.

Owners whose runtime is `()` use `register_stateless(owner)` or `RuntimeSlot::stateless()`. This binds a fixed unit value with no canonical field and no metadata installation, so multiple stateless receiving owners need no placeholder fields or overlapping lenses. Their execution configuration still has registry affinity and generation checks.

`Registry::prepare` borrows the canonical host and executes registered owners through a `TransactionContext`. `OwnerTxn::read` sees prior provisional writes; `iter` returns a stable ID order over canonical and provisional rows, excludes removals, and captures membership and row witnesses. Only the declared owner can write a component type. Repeated writes by that owner coalesce into one final batch operation per row. Runtime slots are copied only when an owner accesses them. Preparation does not clone the host, component store, application state, event history, or unrelated runtime fields.

`Request` names an associated `Response`. `register_request::<Receiver, Request>` installs the receiver's native handler. `OwnerTxn::request` runs it in the same journal, so receiving component changes, runtime changes, allocations and emitted records publish together with their source. Synchronous mutable entry into an already active owner returns an error; `defer` queues a request with response `()` until the initiating stack has returned. Deferred requests drain in FIFO order at preparation completion; scheduled intervals also flush them after due work and before closing callbacks so finalization sees receiving receipts. Failed requests poison the journal even if a caller catches their error. Queued messages retain their causal depth across deferred and topic callbacks. `Registry::set_causal_depth_limit` configures the feedback limit, which defaults to 128 generations. Root operations and sibling recipients have no count limit, so this protection does not depend on population size.

`OwnerTxn::publish<T>` sends an internal typed topic notification. It consumes no public event sequence or revision and creates no gameplay record; the source uses `emit(Event)` for its authoritative public record. `register_subscriber::<Receiver, T>` registers native receiving callbacks in deterministic registration order. Notification callbacks run in FIFO order after the outermost originating stack returns, before the next owner hook, using the same journal. A receiving failure poisons the complete source transaction. Exact Rust topic types route notifications without feature-aware enum matches or source dependencies on recipients. `next_event` on both owner views reports the provisional public record cursor for provenance.

`register_read_request` installs an immutable fact handler receiving `OwnerReadTxn`. This view exposes time, seed, provisional component reads and iteration, the owner's immutable provisional runtime and due queue, shared intermediate facts, and nested readonly requests. Such queries can reenter a currently active owner to inspect its updated facts without releasing that owner's mutable entry protection. Calling a mutable request from this view rejects and poisons the journal. A query depth limit of 128 bounds recursive fact queries while allowing arbitrarily many sequential queries.

`Registry::inspect` runs a registered readonly request against canonical state and returns its native response without publishing events, time or revisions. It rejects mutable receiving handlers. Public application views can translate this response into their own DTOs without executing feature workflows.

Feature-native `DueQueue<Payload>` fields serialize directly in application state. `register_due` assigns each payload type to one owner and binds its queue with a runtime lens. Owners can inspect, schedule, cancel and consume their due work inside the journal. `emit` assigns provisional canonical event sequences, `events_since` borrows committed history plus the provisional suffix, and `reserve_ids` checks a contiguous provisional ID reservation. `revise` explicitly budgets publication revisions.

`Registry::commit` checks registry affinity and registration generation, every consulted runtime and due slot, sparse component witnesses, host affinity and cursor budgets before publishing. After the schema-validated component batch and records are admitted, it installs only precomputed typed runtime and due assignments. Rejected publication preserves all canonical fields. Unrelated metadata and component edits remain independent. Existing `Transaction` and bounded previews remain available for owner APIs that already use prepared batches.

`scheduling::Scheduler` registers owner-native readonly boundary callbacks, mutable advance callbacks taking `ClockSpan`, and typed due callbacks. `register_owner_phased` also accepts optional prepare and close callbacks. Stable `Order` keys determine execution regardless of registration order. A step chooses the earliest requested time, owner deadline or typed due time, then runs ordered preparations, advances, due callbacks and closing callbacks. All phases retain one journal and one set of witnesses, so a late receiving or closing failure preserves the entire interval. Preparation can capture an opening body frame; closing can merge that frame with receipts received during due work. `TransactionContext::set_time` selects the closing clock before mutable callbacks and rejects backwards time or clock selection after mutation has begun. Each committed boundary reserves one revision in addition to native owner publication budgets.

`OwnerTxn::share` retains a native intermediate output only for the current journal. One producer owner can replace each fact type or update it with `fact_mut`; other owners can inspect it with `fact` or expose it through native readonly requests. This permits receipt accumulation without repeatedly cloning an entire frame. For example, an environmental owner can retain its evaluated opening-weather output and answer a consumer's elapsed-day query without application code mapping feature outputs. Shared outputs disappear when preparation seals and never enter snapshots or canonical runtime fields.
