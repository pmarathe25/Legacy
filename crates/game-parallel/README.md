# Parallel engine prototype

This crate is a new, independent simulation kernel, not a replacement for the existing game yet. Run `cargo run -p game-parallel --example run -- content/parallel/example.toml` to load an authored world and advance it. Rules and starting regions are TOML; JSON serialization provides a resumable snapshot. Both loaders validate identifiers and bounds.

A tick partitions mutable state by region. Rayon schedules each region independently, with immutable rules and no shared writes. The ecology owner grows local food, then the people owner generates meal claims, resolves scarce food by a deterministic counter-based priority, and updates health. Dead people neither eat nor recover. Integer arithmetic and identity-based priorities make the result independent of worker scheduling and region ordering. Competing decisions use the tick's phased state, so these semantics intentionally differ from the old engine.

This is a vertical slice, not feature parity: it has no culture, player interface, or GPU backend. Parallelism is limited by the number and balance of regions and by serial work inside each region, memory bandwidth, and scheduling overhead. Linear scaling is a target to measure on representative worlds, not a guarantee. Large contested regions use a parallel priority histogram and select only the boundary bucket; small regions still sort claims. Both paths allocate when claims are contested. Small worlds may run slower with multiple threads.

The intended extension is explicit bulk phases: immutable snapshot reads, per-partition intent generation, deterministic receiver-owned arbitration, then buffered effects applied at a barrier. Cross-region messages must be routed by destination and sorted by stable keys; multi-owner exchanges need explicit reservation/commit semantics. Never perform callbacks that mutate another partition while a phase is running. Dense component columns and fixed-width effect buffers are preferred for numerical kernels that might later run on GPUs. The current structs and sort are CPU-first and are not themselves GPU kernels. Add feature owners and schemas alongside independent tests, and benchmark real contention, skewed populations, and cross-region traffic before replacing the existing application.

For a controlled throughput comparison, run `cargo run --release -p game-parallel --example throughput -- 1 1000 100 100` and repeat with other worker counts. Arguments are workers, regions, people per region, and ticks; append `scarce` to sustain contention for food. This synthetic workload measures only this slice; it does not establish whole-game scalability.

Travel follows directed authored routes, advances needs during transit, and arrives after local simulation phases; shipment stock is reserved at launch and remains in transit when the destination is full. These basic shipment commands do not yet model carriers, property, or consent. World state is currently public: callers that mutate it directly must call `validate` before advancing; this prototype API is not yet hardened for untrusted clients.



Optional `[families]` state enables the [family owner](../game-parallel-families/README.md): individually saved ages, ancestry, diploid genetics, reproductive partnerships, pregnancy, birth and death. Load `content/parallel/families.toml` for an accelerated authored generational fixture. Family-enabled ticks stage region buffers and commit atomically; failed identity, age or counter arithmetic leaves the complete prior world unchanged. Newborns during travel remain with the mother's journey. Baseline worlds without this state keep their existing physical execution and save schema.


For an end-to-end family-enabled workload, run `cargo run --release -p game-parallel --example parallel_benchmarks -- family_throughput 1 100 10000 20`, repeating with other worker counts and region counts. Arguments are workers, regions, starting people, and ticks. The synthetic fixture includes partner formation, conception and births; its intentionally long-lived population is not a long-history or archived-population benchmark. It reports elapsed wall time and actual births. Compare repeated runs on an otherwise idle machine; this example does not establish whole-game scaling.

An optional `[agriculture]` section enables region-owned fields; `content/parallel/farming.toml` is an example. At each tick, eligible residents provide at most one unit of work each. In field-ID order, a worker plants using physical food as seed, tends a growing field, or harvests a ripe crop into regional food storage. Seed and storage claims use the same start-of-phase stock snapshot, so a harvest or planting does not make resources available to other fields until the following tick. Work that lacks seed or storage space is skipped, and ripe crops remain in their fields until they can be stored. Parameters and initial fields are authored in TOML; saves retain field state. The model counts available eligible people; optional volunteer policies represent personal willingness, and the fused host excludes people reserved for other actions. Seasonal windows affect field operations. Individual field assignments, tools, land ownership, and crop species are not yet modeled. The concentrated-farm path uses chunked parallel allocation, with a small serial prefix over chunks. Run `cargo run --release -p game-parallel --example parallel_benchmarks -- farm_throughput 1 100000 100000 100` and compare worker counts; throughput varies with memory bandwidth, workload size, and the rest of the enabled world.


Shipment delivery resolves storage claims by destination, then by shipment ID, using parallel chunks and a prefix over their cargo totals. Partial deliveries stay in transit. The synthetic `cargo run --release -p game-parallel --example parallel_benchmarks -- shipment_throughput 1 100000 100` benchmark models an external sink clearing storage each tick and checks food conservation; repeat with other worker counts to compare concentrated traffic. It does not measure carriers, trade, or end-to-end game scaling.

Run `cargo run -p game-parallel-cli -- content/parallel/farming.toml` for an interactive experimental session; use `help` for commands. The interface advances ticks, inspects regions, starts individual travel and food shipments, and saves or loads JSON snapshots. Saves are written to a temporary file before replacing the target. Input can also be piped from a script. A failed command reports an error and leaves the session open; a `run` that encounters a failed tick retains earlier successful ticks. Paths are currently single whitespace-free arguments. This administrative interface does not yet implement ruler-bound control, subjective knowledge, or the full game.


Travel arrivals are routed at a barrier by destination and person ID. Compare the concentrated-arrival workload with `cargo run --release -p game-parallel --example parallel_benchmarks -- travel_throughput 1 100000 20` and other worker counts; add `meals` to include automatic provision consumption; it reports repeated step medians, not whole-game throughput. Personal holdings can travel with their owner; existing shipments are still independent of carriers.

Optional `[cargo]` data sets a per-person food carrying capacity; `content/parallel/cargo.toml` is an example. Living people can pick up food from their current region, carry it on routes, eat it during travel, and deposit it at their destination. Food remains with a deceased holder, including during travel, until a living person in the same region recovers it into storage. Pickup, deposit and recovery are explicit administrative commands (`take`, `store`, `eat`, and `recover` in the CLI); NPCs do not yet plan or consent to those transfers. With `auto_eat_travel = true` in `[cargo]`, a living traveler consumes one carried meal when their updated hunger reaches the meal threshold, before starvation damage. The default is false. With `auto_pack_travel = true`, each departing person requests enough food for projected hunger over the route, accounting for current holdings and carrying capacity. Source stock is reserved in person-ID order and may be allocated partially; the departure itself is not rejected for insufficient food. `content/parallel/cargo_auto.toml` enables both policies. People do not yet choose routes autonomously, and this policy does not model consent or ownership. Personal holdings are saved and validated, but ownership rights and general goods are not modeled.


The concentrated departure benchmark `cargo run --release -p game-parallel --example parallel_benchmarks -- packing_throughput 1 100000 10` includes request validation, provision allocation, and departure. Repeat with other worker counts; it measures a synthetic one-region batch, not full-game scalability.

Optional `[social]` content enables the [social owner](../game-parallel-social/README.md); `content/parallel/social.toml` demonstrates mutually willing local encounters and saved familiarity. The synthetic `cargo run --release -p game-parallel --example parallel_benchmarks -- social_throughput 1 100 10000 10` measures complete ticks with encounter history enabled; repeat with other worker counts and region counts.

Optional `[knowledge]` data enables [personal observations](../game-parallel-knowledge/README.md); `content/parallel/knowledge.toml` demonstrates local evidence and a report received during an encounter. The administrative CLI command `knowledge PERSON` displays that person's stored records. To include knowledge in the social throughput fixture, append `knowledge`, for example `cargo run --release -p game-parallel --example parallel_benchmarks -- social_throughput 1 100 10000 10 knowledge`.


Optional `[autonomy]` data enables [knowledge-driven travel](../game-parallel-autonomy/README.md); `content/parallel/autonomy.toml` provides a small fixture. The administrative `decisions` command displays the latest departure outcomes. Compare workers with `cargo run --release -p game-parallel --example parallel_benchmarks -- autonomy_throughput 1 10000 10`; this fixture measures a whole decision-and-departure tick but not the complete game.


Optional `[production]` data enables [reserved workshop jobs](../game-parallel-production/README.md). `content/parallel/workshop.toml` defines timber, planks and a timed recipe. Work, cancellation and reassignment are available through the administrative CLI. Run `cargo run --release -p game-parallel --example parallel_benchmarks -- production_throughput 1 100000 10` and compare worker counts; this synthetic concentrated workload includes validation and the whole tick. Results are not evidence of full-game scaling.

Nonfood goods can be carried on a person via `[goods_cargo]`; `pickup-good PERSON GOOD QUANTITY`, `goods PERSON`, and `deposit-good PERSON GOOD QUANTITY` expose the local transfer actions. Carried goods stay with the person during travel. Transfer batches are atomic and share a pre-transfer stock snapshot. A living local person can recover goods from a deceased holder using `recover-good ACTOR DECEASED GOOD QUANTITY`; property rights are not yet modeled.

`[market]` enables saved offers between living, local people. A proposer may withdraw; the recipient can respond directly or through a personal policy in the fused host. One-sided requests can motivate physical transfers through the recipient's own valuation, fear, or obligation without implying approval. Transfers recheck actual possessions and carrying capacity, so stale offers cannot create goods. The CLI exposes `offer`, `offers`, `accept`, `decline`, and `withdraw`.

`cargo run --release -p game-parallel --example parallel_benchmarks -- economy_throughput 1 100000` measures a full production, pickup, travel and deposit lifecycle; repeat with different worker counts. `production_start_throughput`, `production_throughput` (append `scarce` for contested storage), `goods_transfer_throughput`, and `market_throughput` isolate individual boundaries. These synthetic fixtures do not establish whole-game scaling or feature completeness.

`[autowork]` enables authored per-person recipe policies with contested input reservations; `content/parallel/autowork.toml` supplies a fixture. Optional `[lineage]` follows the current incarnation through death and a subsequent actual birth, with a deterministic lowest-ID newborn selection for this prototype. The [guardian prototype](../game-parallel-guardians/README.md) follows and mentors the current incarnation, but full guardian agency, ruler control, and invocation effects remain unimplemented.

The persistent [compiled block runtime](../game-parallel-blocks/README.md) and its CLI execute the same experimental owner set without reconstructing physical blocks every tick. Its focused benchmarks report separate phases and should be repeated across worker counts; current end-to-end results do not yet satisfy the desired scaling target.


The experimental lineage can also contain an `[invocation]` owner; `content/parallel/invocation.toml` gives fixture values. The compiled CLI supports `invoke`, `invocation`, `memories`, `accept-invocation`, and `dismiss-invocation`. Time acceleration stops at a saved warning before unaccepted burden or control loss. Borrowed records stay in the old life rather than being copied into the current person's knowledge. Strain effects, inherited capabilities, and a complete autonomous ruler policy remain to be implemented.


Optional `[property]` data records claims and permitted access to nonfood regional stocks. The fused host also allows people to take or work with claimed inputs without permission, with witnessed consequences. Optional `[institutions]` is an experimental fixed voting-body model; its declarations do not themselves prevent physical exchanges. It is not yet a general model of institutions emerging from individual action, and social invention and enforcement remain open work.
